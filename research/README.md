# Реплика и сверка

`replica.py` — Python-повторение каскада индикатора «Тренажёр v8». Нужна, чтобы
измерять последствия правок на реальных данных до того, как они попадут в Pine.

`verify.py` — сверка реплики с CSV-экспортом индикатора из TradingView.

```
cd research && python3 verify.py ../data/XAUUSD_5m.csv ../data/XAUUSD_1h.csv
```

## Точность реплики

После прогрева состояния (первые ~200 баров экспорта индикатор уже «тёплый»,
у реплики очередь и выборка порога пустые):

| ТФ | совпало | расхождений |
|----|---------|-------------|
| 5m | 2915/2922 = **99.76%** | 6 — порог авто-режима на прогреве, 1 — граница допуска |
| 1H | 205/206 = **99.51%** | 1 — граница допуска |

Единственное содержательное расхождение — бар 8463 на 5m: `Δupper` ровно
`4.000000` при допуске `4.0`. Сравнение `<=` на границе решается разным
округлением в Pine и Python. 1 бар на 20 000.

## Настройки, с которыми сделаны экспорты

Подобраны перебором по совпадению вердиктов — в файлах они не записаны:

| | порог | предохранитель | фильтр режима |
|---|---|---|---|
| 5m | **авто** (растущее окно) | выкл | вкл |
| 1H | **фикс ≈ 0.350%** (не 0.317) | выкл | вкл |

Файлы сняты с разными настройками и напрямую не сопоставимы.

## Что установлено на данных

1. **Шаблон #10 недостижим.** `24.5+28.4+71.6 = 124.5`, а сумма долей
   body/upper/lower всегда ровно 100. За 22 677 баров обоих файлов — 0
   срабатываний; единственный мёртвый из 40. Похоже на опечатку: `lower`
   должен быть `47.1`.
2. **Равные пивоты теряются.** При `vw1 == vw2` условия `<` и `>` оба ложны,
   метка не создаётся и не попадает в очередь. На 5m — 3 случая (двойные
   вершины в тик), на 1H — 0.
3. **Тренд D3 перезапускает сам себя.** После смерти телом `d3_lastH`/`d3_lastL`
   не сбрасываются, и следующий же бар возрождает тот же тренд на том же
   уровне без новой пары меток 5/5.
4. **Порог 0.317% устарел на обоих ТФ.** Текущий P80 триггерных баров:
   5m — 0.137%, 1H — 0.544%. Фикс 0.317 на 1H режет 56% триггеров вместо 20%,
   на 5m — 1.1%.

## Почему 5m не чинится буфером

Соблазн: заменить буфер «0.1% цены» на долю диапазона бара. На бумаге
5m даёт −37.1R → +68.4R. Это мираж:

* риск падает до $1.39 при среднем баре $4.98 — стоп **уже одного бара**;
* 55% сделок закрываются на первом же баре после входа, то есть исход целиком
  определяется порядком тиков внутри бара, а OHLC его не содержит;
* спред $0.30 (обычный для XAUUSD) съедает 21.6% риска и превращает +68.4R
  в −36.0R.

На 1H та же проверка безобидна: риск $8.99 — половина бара, спред $0.30 это
3.3% риска, +14.3R → +12.9R.

Вывод: дело не в буфере. На 1H геометрия работает — стоп около половины бара,
магнит в 3R. На 5m тот же каркас даёт либо риск в 1.16 бара (WR падает до
11.5%), либо риск меньше спреда. Чтобы честно проверять 5m, нужны данные
мельче 5m (1m или тики) для разрешения порядка SL/TP внутри бара.

# Сверка Pine ↔ engine_v3/v4/v5

Разбор построчный. Совпадающее не перечисляю, только расхождения и то, что
про них нужно знать.

## Единый файл движка

`engine.py` заменяет связку `engine_v3.py` + `engine_v4.py` + `engine_v5.py`.
Поведение живого кода не тронуто, выброшен только мёртвый (`COST`, `ATR_WIN`,
`ATR_MULT`, `decide_point`). Оригиналы оставлены в репозитории исключительно
ради проверки эквивалентности:

```
python3 test_engine_merge.py ../data/XAUUSD_1h_engine.csv ../data/XAUUSD_5m_engine.csv
```

| файл | v4 | v5 | вердиктов сверено | расхождений |
|---|---|---|---|---|
| 1H | 84 сделки, +3.0R | 59 сделок, +7.0R | 471 | **0** |
| 5m | 130 сделок, −48.7R | 102 сделки, −43.8R | 3186 | **0** |

Добавлено к оригиналу: `build_engine(path, trig=...)` умеет считать триггеры по
шаблонам формы, когда колонки `триггер` в файле нет — иначе движок не работает
на выгрузках из TradingView. При `trig='column'` поведение ровно как в v3.

## Главное: шаблонов свечей в движке нет

`engine_v3.build_engine` берёт триггеры готовой колонкой из CSV:

```python
TRIG = (df['триггер'].values == 1) if 'триггер' in df.columns else np.zeros(N, bool)
```

40 шаблонов `tb/tu/tl` существуют **только в Pine**. Эталон «939 сделок,
+53.2R» посчитан по колонке `триггер` в `xau_1h_master.csv`, а не по шаблонам.

Отсюда два следствия:

* Код, породивший колонку, найден: `indicator/trigger_alert_v2.pine`. Массив
  `tl` там содержит ту же `71.6` на позиции 10. То есть шаблон #10 мёртв **во
  всей цепочке**: триггерный индикатор → выгрузка колонки `триггер` →
  `xau_1h_master.csv` → движок → эталонные 939 сделок. Починка #10 разойдётся
  не только с индикатором, но и со всей историей результатов проекта.
* Заявленная в шапке «Тренажёра» сверка «9416/9416 повердиктно» не могла быть
  сделана через `engine_v3.py` в одиночку — она требовала мастер-файла. Сам
  `xau_1h_master.csv` пока не найден, поэтому воспроизвести эталонные 939
  сделок нечем.
* Шаблоны и код пивотов продублированы в двух Pine-файлах —
  `trigger_alert_v2.pine` и `trener_v8.pine`. Два источника правды, разъедутся
  при первой же правке одного из них.

| # | Что | Pine | engine_v3/v4 | Влияние на данных |
|---|-----|------|--------------|-------------------|
| 1 | Ничьи в пивотах | `ta.pivothigh`: `>=` слева, `>` справа | `fp()`: строго `>` с обеих сторон | 5m: 103→105 сделок, −44.8→−46.8R. 1H: нет |

| 3 | Источник порога | константа 0.317 либо растущее окно | `np.percentile` по **всей** истории — заглядывание вперёд | порог 0.317 верен только для мастер-файла |

Оба расхождения, которые вообще проявились (#1, #2), латентны: на присланных
данных почти не видны, но останутся минами.

## Что совпадает точно

Проверено построчно и подтверждено репликой:

* порядок каскада: заморозка → размер → тренд → слом → стоп → магнит → запреты
  (в `engine_v3.decide_point` размер стоял **перед** заморозкой; `decide_v4`
  порядок поменял, и Pine следует именно v4 — это верно);
* направление по последней метке: `HL/LL → LONG`, `LH/HH → SHORT`;
* асимметрия порога тренда `3/5` только для шортов от HH, иначе `4/5`
  (`tmin = 3 if last == 'HH' else 4`) — в Pine `up >= (lastL == "HH" ? 3 : 4)`;
* асимметрия слома: ловятся только `HH→LL` и `LL→HL`, зеркальных нет —
  **это не потеря в Pine, так в движке с v3**;
* равные пивоты теряют метку: `mk()` пропускает при `H[i] != prev` ложном,
  Pine — при `vw1 == vw2`. **Дефект общий для обоих**, не расхождение;
* первая метка каждой стороны не создаётся (нет `prev` / `valuewhen(...,1)` = na);
* `lag = i - conf`, где `conf = бар пивота + right`;
* буфер стопа 0.1% (`BUF=0.001`, `L[i]*0.999`);
* магнит: первая метка нужной стороны с RR ≥ 3, ближние с RR < 3 перепрыгиваются;
* одновременное касание SL и TP в баре = SL;
* список запретов `LL>HH`, `HH>LH`, `LL>LH>HL`, `HH>LL>LL` (порядок перебора
  различается, но пары взаимоисключающие — на результат не влияет);
* число одновременных позиций не ограничено ни там, ни там (в шапке Pine
  «до 5» — это наблюдение, а не лимит).

## Мёртвый код в движке

* `COST = 0.20` объявлена в `engine_v3` и **нигде не используется** — спред и
  комиссия не моделируются ни в одном из трёх движков.
* `ATR_WIN`, `ATR_MULT` — помечены как неиспользуемые самим автором.
* `GRID = 5.0` и `stop_variants` считают 4 варианта стопа, но `decide_v4`
  жёстко берёт вариант «свеча»; остальные три не используются.
* `engine_v3.decide_point` целиком не вызывается из v4/v5 — это предыдущее
  поколение логики, оставленное для самотеста.
